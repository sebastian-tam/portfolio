The Challenge

Zippe's competitor — one of the UK's largest ride-hailing networks — publishes no public pricing API and no fare documentation. The goal was to build a system capable of mapping their entire dynamic pricing surface across 1,960 route pairs and 1,855 Points of Interest in Bath, exposing surge patterns, route-specific pricing, and the relationship between the competitor's fares and the legally-defined Hackney Carriage council tariff.

The core constraint: every fare observation had to be obtained programmatically by authenticating against the competitor's internal mobile API using a captured JWT bearer token (renewed weekly via HTTP Toolkit iOS interception). The system had to handle token expiry, service-area rejections, concurrent database writes, and routing distance calculations — all without any external paid APIs.

Research question: Can we build a predictive model that accurately estimates the competitor's live price for any route, at any time, across any vehicle class — using only historically observed fares?

The Architecture — 4 Automated Agents

Four automated Python scripts run via macOS launchd, coordinated by a file-based IPC mechanism:

competitor_pricer.py
~2,660 routes/hr; touches fares_done.marker at ~:50 when DB writes complete

competitor_retrain.py
Retrains XGBoost ratio model hourly on rolling 24h test window; 24 features
:10*
competitor_pilot_test.py
Fires every 3h; polls fares_done.marker; validates all 4 models against 500 live routes
:57
competitor_analysis.py
Updates accuracy metrics, trend JSONs, HTML report; proceeds on fresh marker
:5001
osrm-routed
Self-hosted OSRM (great-britain.osrm, 7.1GB) — launchd-managed, auto-restart on crash

IPC Coordination: fares_done.marker decouples the 50-minute fare-write loop from post-processing — pilot polls every 5 min (90-min max wait); analysis proceeds immediately at :57 once marker is fresh. Prevents both agents from reading a partially-written database.

Storage: SQLite WAL-mode database with 4 tables: competitor_fares (4,110,514 rows), competitor_pois (1,855 POIs), pilot_results (29,584 live comparisons), run_log (330 runs). ~408k driving distances cached to driving_distances.json.

Routing: Fully migrated from Google Maps to self-hosted OSRM (4 Jun 2026). Zero external API calls. Cache → OSRM localhost:5001 → haversine fallback. 320,623 historical distances backfilled via OSRM Table API.

Four Pricing Models — Baseline to ML
Model A
Formula v3 — Baseline Linear
max(min_fare, base + rate × miles) per-vehicle params fitted from off-peak data. Structurally breaks on short trips (<5mi).
MAPE: 23.9% (excl. <5mi: 68–90%)
Model B
Route Lookup — Empirical Cache
Median observed price per (pickup, dest, day-type) triple. Back-calculates to off-peak base ÷ surge. 100% route anchor coverage.
MAPE: 9.6–17.5%
Model C
Council Ratio — Structural Anchor
council_tariff(dist,T1) × ratio × CTR_SURGE[hour]. Ratio interpolated linearly between band midpoints. Generalisable to unseen routes.
MAPE: 13–18%
Model D LIVE
XGBoost Ratio-Target — ML
Predicts price / council_ratio_est (clipped 0.3–5.0); 24 features; hourly retrain on rolling 24h window. Live since 28 May 2026.
Retrain MAPE: 8–10% (stable)

Frequently Asked Questions

What machine learning models does Sebastian Tam use for pricing predictions?

Sebastian Tam builds a sophisticated pricing prediction system using four progressive models: Formula v3 (baseline linear model with 23.9% MAPE), Route Lookup (empirical cache with 9.6–17.5% MAPE), Council Ratio (structural anchor with 13–18% MAPE), and XGBoost Ratio-Target (ML model achieving 8–10% MAPE, live since May 28, 2026). The XGBoost model is the most advanced, predicting price-to-council-ratio with 24 engineered features and hourly retraining on a rolling 24-hour window of production data.

How does Sebastian Tam's system use competitor fare data?

Sebastian's pricing system maintains a historical database of competitor fares with 4,110,514 rows of competitor pricing data and 1,855 points of interest (POIs). The system runs a 50-minute fare-write loop that collects competitor prices, which are then used by the XGBoost model as the primary feature for route-based pricing intelligence. Route memory dominates all other features, allowing the model to learn the competitor's own pricing logic from historical observations. The system also caches 408,000+ driving distances to avoid external API dependencies.

What is the technical architecture of Sebastian Tam's ML pricing system?

The architecture is built on Python 3.x with XGBoost for predictions, SQLite WAL-mode database for storage, self-hosted OSRM for routing (fully migrated from Google Maps on June 4, 2026), and FastAPI for API exposure. The system uses launchd for process management and HTTP Toolkit for debugging. IPC coordination uses file-based markers (fares_done.marker) to decouple the 50-minute fare-write loop from post-processing, with the pilot polling every 5 minutes (90-minute max wait). Pandas is used for data transformation and analysis.

How often is Sebastian Tam's XGBoost pricing model retrained?

Sebastian's XGBoost Ratio-Target model undergoes hourly retraining on a rolling 24-hour window of production data. This frequent retraining schedule ensures the model adapts to real-time market changes and competitor pricing patterns. The model maintains stable performance with 8–10% MAPE (Mean Absolute Percentage Error) across retrain cycles, indicating that the hourly update cadence successfully captures temporal pricing dynamics without overfitting.

What databases and technologies power Sebastian Tam's pricing system?

The system uses SQLite with WAL (Write-Ahead Logging) mode for efficient concurrent access to four tables: competitor_fares (4,110,514 rows), competitor_pois (1,855 locations), pilot_results (29,584 live comparisons), and run_log (330 runs). Additional storage includes 408,000+ cached driving distances in driving_distances.json to eliminate external API dependency. Routing is fully self-hosted using OSRM (Open Source Routing Machine) with localhost:5001, replacing Google Maps entirely. This architecture provides fast, reliable, and cost-effective pricing predictions without relying on external services.
