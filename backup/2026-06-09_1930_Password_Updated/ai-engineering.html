The Challenge

Zippe's competitor — one of the UK's largest ride-hailing networks — publishes no public pricing API and no fare documentation. The goal was to build a system capable of mapping their entire dynamic pricing surface across 1,960 route pairs and 1,855 Points of Interest in Bath, exposing surge patterns, route-specific pricing, and the relationship between the competitor's fares and the legally-defined Hackney Carriage council tariff.

The core constraint: every fare observation had to be obtained programmatically by authenticating against the competitor's internal mobile API using a captured JWT bearer token (renewed weekly via HTTP Toolkit iOS interception). The system had to handle token expiry, service-area rejections, concurrent database writes, and routing distance calculations — all without any external paid APIs.

Research question: Can we build a predictive model that accurately estimates the competitor's live price for any route, at any time, across any vehicle class — using only historically observed fares?

The Architecture — 4 Automated Agents

Four automated Python scripts run via macOS launchd, coordinated by a file-based IPC mechanism:

~2,660 routes/hr; touches fares_done.marker at ~:50 when DB writes complete

Retrains XGBoost ratio model hourly on rolling 24h test window; 24 features

Fires every 3h; polls fares_done.marker; validates all 4 models against 500 live routes
:57
competitor_analysis.py
Updates accuracy metrics, trend JSONs, HTML report; proceeds on fresh marker
:5001
osrm-routed
Self-hosted OSRM (great-britain.osrm, 7.1GB) — launchd-managed, auto-restart on crash

IPC Coordination: fares_done.marker decouples the 50-minute fare-write loop from post-processing — pilot polls every 5 min (90-min max wait); analysis proceeds immediately at :57 once marker is fresh. Prevents both agents from reading a partially-written database.

Storage: SQLite WAL-mode database with 4 tables: competitor_fares (4,110,514 rows), competitor_pois (1,855 POIs), pilot_results (29,584 live comparisons), run_log (330 runs). ~408k driving distances cached to driving_distances.json.

Routing: Fully migrated from Google Maps to self-hosted OSRM (4 Jun 2026). Zero external API calls. Cache → OSRM localhost:5001 → haversine fallback. 320,623 historical distances backfilled via OSRM Table API.

Four Pricing Models — Baseline to ML
Model A
Formula v3 — Baseline Linear
max(min_fare, base + rate × miles) per-vehicle params fitted from off-peak data. Structurally breaks on short trips (<5mi).
MAPE: 23.9% (excl. <5mi: 68–90%)
Model B
Route Lookup — Empirical Cache
Median observed price per (pickup, dest, day-type) triple. Back-calculates to off-peak base ÷ surge. 100% route anchor coverage.
MAPE: 9.6–17.5%
Model C
Council Ratio — Structural Anchor
council_tariff(dist,T1) × ratio × CTR_SURGE[hour]. Ratio interpolated linearly between band midpoints. Generalisable to unseen routes.
MAPE: 13–18%
Model D LIVE
XGBoost Ratio-Target — ML
Predicts price / council_ratio_est (clipped 0.3–5.0); 24 features; hourly retrain on rolling 24h window. Live since 28 May 2026.
Retrain MAPE: 8–10% (stable)

  • XGBoost ratio-target model achieves 8–10% MAPE at stable retrain state — competitive across all time slots and distance bands
  • Afternoon surge peak quantified: +21% at 15:00 UTC (1.218× multiplier), morning peak +10% at 07:00
  • The competitor undercuts council tariff by 24.3% on 20–30mi and 17.5% on 10–20mi routes
  • The competitor charges a premium over council on short trips: +12.9% on <5mi, +6.2% on 5–7.5mi

  • 100% route anchor coverage: 1,960/1,960 routes have ≥3 scrapes for empirical price lookup
  • Zero external API dependencies: self-hosted OSRM, Google Maps fully removed, JWT token renewed weekly via HTTP Toolkit iOS interception

RAG-based AI Agentic Enterprise System

Fully local, privacy-first RAG AI system covering four core domains — deployed for inhouse operations and clients.

"Implemented a RAG-based AI Agentic Enterprise system for pricing research, QA & UAT, DBS and CRM compliance support — deployed for both inhouse operations and clients, with all data kept entirely on-premises."
System Overview & Architecture

The system was built on a fully local stack using AnythingLLM and Ollama to ensure no proprietary business data left the organisation's infrastructure — a critical requirement for DBS compliance and competitive sensitivity. Deployed for both inhouse operations and external clients.

The RAG pipeline ingests, indexes, and retrieves from internal document stores, enabling natural language queries across historically siloed datasets spanning pricing, marketing, QA, and compliance domains.
